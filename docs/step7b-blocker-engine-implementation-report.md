## Implementation Report

Implements the design approved in `docs/step7a-blocker-engine-audit.md`. Section 2's

document had explicitly left open (a `blocker_conflicts` table, and demo-scenario DB seeding);
both are recorded below with their rationale, not silently resolved.

## C. Database migration

Autogenerated via `alembic revision --autogenerate`, reviewed, then applied. Adds exactly three
tables, all additive:

- **`blockers`** — append-only (mirrors `StatutoryClockRecord`): `id` (Blocker's own
  server-generated ID, not a second DB-assigned one), `evaluation_run_id` (ties every row from one
  `evaluate_case` call together — see below), `case_reference`, nullable `project_id`/`parcel_id`
  FKs with `ondelete='SET NULL'` (never CASCADE — a project/parcel deletion never destroys blocker
  history), `blocker_type`, `status`, `severity`, `owner_role`, `responsible_authority`,
  `affects_clock`/`affected_clock_ids`, `affects_possession`, `affects_project`,
  `downstream_extent` (JSON), `is_primary`, `ranking_basis` (JSON), resolution fields,
  `engine_version`, `calculation_date`, `notes`, `calculated_at`, `created_at`. Indexes on every
  column a `WHERE` clause in `db_crud.py` actually filters on.
- **`blocker_evidence`** — append-only, `blocker_id` FK nullable + `SET NULL` (an evidence row is
  historical and should outlive its parent, the same discipline `AuditLog.parcel_id` already
  uses).
- **`blocker_actions`** — the one **mutable** table (deliberate deviation, documented in its own
  docstring): `status` can change over time, mirroring the existing, production
  `CaseAction.status` PATCH-able pattern. No PATCH endpoint is exposed in this step (see M).

**Deviation from the Step 7A design document, reported explicitly:** no `blocker_conflicts` table
was created. The design doc flagged this as "the one judgment call reasonable people could make
differently" (§Q). This implementation represents a conflict as `BlockerRecord.status ==
'CONFLICTED'` with its competing `BlockerEvidenceRecord` rows tagged
`relation IN ('SUPPORTS','CONTRADICTS')` — fully queryable without a separate table, and
consistent with the fact that nothing in `detection.py`/`ranking.py`/`engine.py` ever constructs a
distinct `BlockerConflict` object (the pure dataclass still exists in `models.py` as a documented
future extension point, just unused). This was a genuine implementation-time simplification, not
an oversight.

**Verification performed:**
- Applied to a fresh throwaway SQLite database from empty — all three tables created cleanly, in
  correct dependency order (`blockers` before its two FK-dependent children).
- Applied to the real `backend/kshetra.db` (`alembic upgrade head`, `9e314c0fd8a0` →
  `ee05da00ead9`) — succeeded; every pre-existing table's row count is unchanged (`projects`: 1,
  `parcels`: 8, `alerts`: 4, `case_actions`: 4, `audit_logs`: 3, `predictions`: 0, `rule_sets`: 8,
  `acquisition_events`: 7, `court_stay_events`: 1, `extension_evidence`: 1, `event_conflicts`: 1,
  `statutory_clocks`: 6 — all identical before/after).
- The new `blockers`/`blocker_evidence`/`blocker_actions` tables are left **empty** in
  `kshetra.db` — see N for why no demo data was seeded into the shared database.

## D. B1 implementation

`detection.detect_b1(clock: legal.clock_engine.StatutoryClockResult) -> BlockerEvaluation`. Takes
the Step 6B `StatutoryClockResult` dataclass **directly** — imported, never re-implemented — and
performs no date arithmetic and no deadline computation anywhere in this package.

Exact mapping implemented, per the approved design (`docs/step7a-blocker-engine-audit.md` §C):

| `ClockStatus` / `ConsequenceClass` | Outcome | Notes |
|---|---|---|
| `INSUFFICIENT_BASIS` | `INSUFFICIENT_EVIDENCE` | Never silently absent. |
| `CLOCK_CERTAIN` / `PROCESS_DELAY` | `EVIDENCE_OF_NO_BLOCKER` (no row) | Comfortably ahead. |
| `CLOCK_CERTAIN` / `CLOCK_AT_RISK` | `DETECTED`, severity HIGH (≤14 days) or MODERATE | |
| `CLOCK_UNCERTAIN` | `SUSPECTED`, **hard-capped**, never HIGH/CRITICAL | Verified by
  `B1UncertainClockTests`. |
| `EXTENSION_UNVERIFIED` | `DETECTED`, HIGH | |
| `APPARENT_LAPSE` / `APPARENT_LAPSE` | `CONFIRMED`, CRITICAL, with the exact clock-engine
  disclaimer text ("NOT a determination...") carried into `Blocker.notes` | |
| `APPARENT_LAPSE` / `CLOCK_EXPIRED` | `DETECTED` (never `CONFIRMED`) | |
| `LEGACY_1894` | `INSUFFICIENT_EVIDENCE` or `SUSPECTED`, never `CONFIRMED` | |

`demo_scenarios.scenario_e_multiple_blockers` additionally drives a **real** `RFCTLARR_S25_AWARD`
`RuleSet` through `legal.clock_engine.compute_statutory_clock` (no extension claimed, deadline
long passed) to `APPARENT_LAPSE`, proving B1 end-to-end against the live Step 6B engine, not just
hand-built `StatutoryClockResult` fixtures.

## E. B2 implementation

`detection.detect_b2(parcel: ParcelEvidenceInput, ..., secondary_ownership_observation=None)`.
`ownershipDispute != 'No'` and `encumbranceStatus == 'Pending Partition'` fold into one bucket
(they plausibly describe the same fact); `documentStatus`/`mutationStatus`/other
`encumbranceStatus` values are separate buckets. 0 buckets + all fields populated + clean →
`EVIDENCE_OF_NO_BLOCKER` (downgraded to `INSUFFICIENT_EVIDENCE` if `recordConfidence == 'Low'`); 0
buckets + missing fields → `NO_EVIDENCE`; 0 buckets + ambiguous (e.g. `'Pending Verification'`) →
`INSUFFICIENT_EVIDENCE`; 1 bucket → `SUSPECTED`; ≥2 buckets → `DETECTED`. **`CONFIRMED` is
architecturally unreachable** from bare `Parcel` fields — every code path that would otherwise
qualify carries an explicit note citing Data Gap row B2-1 (`docs/step7a-blocker-engine-audit.md`
§U), and `B2NoFalseConfirmationTests` asserts this directly with every qualifying signal maxed
out simultaneously.

`CONFLICTED` is reachable via the `secondary_ownership_observation` parameter — today's `Parcel`
schema carries exactly one value per field (confirmed in the Step 7A audit), so there is no
"two competing government records" shape to disagree with itself; this parameter models the case
where KSHETRA genuinely holds a second, independently-obtained reading, and a same-tier
disagreement is reported as `CONFLICTED` with both readings preserved (never one overwriting the
other), reusing `legal.conflicts`'s own philosophy.

## F. B3 implementation

`detection.detect_b3(parcel, ...)`. `compensationStatus == 'Pending'` alone is explicitly **not**
treated as dispute evidence (`NO_EVIDENCE`) — `B3PendingIsNotAutomaticallyDisputeTests` directly
tests the anti-pattern guard the brief named. Only `'Under Dispute in LA-RA Authority'` raises
`DETECTED`; `'Determined'`/`'Disbursed 100%'` → `EVIDENCE_OF_NO_BLOCKER`; `'Disbursed 40%'` →
`INSUFFICIENT_EVIDENCE` (ambiguous — ordinary phased payment or a stalled dispute, current data
cannot distinguish). `CONFIRMED` is unreachable (same reasoning as B2); every DETECTED/
INSUFFICIENT result's notes cite Data Gap rows B3-1/B3-2/B3-3. R&R fields and contested-amount
(offered-vs-claimed) evidence are not represented in `ParcelEvidenceInput` at all — no code
attempts to evaluate what doesn't exist. No S.30/S.38 `RuleSet` was created or touched; B3 sets
`affects_possession=True` purely as the documented interface hook (§L of the audit), pointing at
no clock (`affected_clock_ids=()`), since none exists yet.

## G. B4 implementation

`detection.detect_b4(parcel, ..., court_stay: Optional[legal.stays.CourtStayEvent] = None)`.
Three evidence sub-types tracked separately (`B4EvidenceSubtype`): physical obstruction (keyword
match over `fieldVerificationNotes`, only when `fieldVerified == True`), court restraint, and
regulatory/environmental precondition (`environmentalZone`/`waterBodyAdjacent` — never conflated
with a physical obstruction). Not every litigation case is B4: `Disposed` cases and cases without
`interimInjunction` raise nothing (`B4UnrelatedLitigationTests`). Scope-matching reuses
`legal.stays.StayScope` directly rather than inventing a second model
(`_stay_covers_parcel`) — `PROJECT` scope always covers, `PARCEL` scope checks
`affected_parcels`, `STAGE` scope is conservatively treated as **not** covered (this detector has
no "current process stage" to compare against). **The one path to `CONFIRMED`** in this whole
implementation outside B1: a `VERIFIED`, in-scope `legal.stays.CourtStayEvent` supplied to
`detect_b4` — bare `courtCaseStatus`/`interimInjunction` fields alone are capped at `DETECTED`
(`B4ScopedCourtStayTests.test_bare_court_fields_fallback_never_reach_confirmed`). Owner is
deliberately not single-valued: physical + court evidence together yields a joint
"Field Team AND Legal Desk" owner string (`B4DualOwnerTests`).

## H. Blocker state machine

Implemented exactly as specified: `DETECTED`, `SUSPECTED`, `CONFIRMED`, `INSUFFICIENT_EVIDENCE`,
`CONFLICTED`, `RESOLVED` (`enums.BlockerStatus`) are the persisted states. `NO_EVIDENCE` and
`EVIDENCE_OF_NO_BLOCKER` are **not** members of that enum — they live in the separate
`BlockerEvaluationOutcome` enum precisely so they can never be confused with, or silently
collapsed into, "no blocker" (`enums.py`'s module docstring quotes the brief's own instruction
verbatim). Every detector always returns a `BlockerEvaluation` (never `None`), so a clean or
insufficient outcome is exactly as inspectable and testable as a raised one — verified by
`B1CleanTests`, `B2NoEvidenceTests`/`B2CleanTests`, `B3NoEvidenceTests`/`B3CleanTests`,
`B4NoEvidenceTests`/`B4CleanTests`.

## I. Evidence / provenance

Every `BlockerEvidence` row carries `source_type` (a `legal.enums.SourceType` value — **imported,
never redefined**; `blockers/enums.py` re-exports it and `SOURCE_AUTHORITY_RANK` from
`legal.enums` rather than declaring a second hierarchy), `verification_status` (reusing
`legal.enums.EvidenceVerificationStatus`), `source_ref_type`/`source_ref_id` (a pointer to the
underlying clock/parcel-field/field-verification/court-stay record), `description`, `relation`
(SUPPORTS/CONTRADICTS/AMBIGUOUS), and timestamps where available. Confirmed by
`EngineProvenancePreservationTests`: every raised blocker in a live engine run carries at least
one evidence row with a non-empty description and a valid `EvidenceVerificationStatus`.

## J. Conflict resolution

Implemented for B2 via `secondary_ownership_observation` (see E) — both competing evidence rows
are preserved (never one overwriting the other), `status = CONFLICTED`, and `ranking.py` never
promotes a `CONFLICTED` blocker to primary regardless of severity
(`RankingIneligibleStatusesTests.test_conflicted_never_selected_as_primary_even_with_critical_severity`).
When only `CONFLICTED`/`INSUFFICIENT_EVIDENCE` blockers exist for a case, `primary_blocker_id` is
explicitly `None` with an explanatory `note` — never an arbitrary pick
(`test_only_conflicted_and_insufficient_yields_no_primary`, and Demo Scenario F end-to-end).

## K. Primary/secondary ranking

`ranking.rank_blockers`, sort key **in this order**: (1) severity (`BLOCKER_SEVERITY_RANK`), (2)
confidence tier (`CONFIRMED > DETECTED > SUSPECTED`), (3) downstream possession impact
(`affected_parcel_count`, unknown treated as non-penalizing), (4) `blocker_type` — a fixed,
documented **last-resort** tiebreak reached only when 1–3 are genuinely tied, (5) `blocker_id` —
final tiebreak for total ordering. **Not** a hardcoded `B1 > B2 > B3 > B4`:
`RankingSeverityFirstTests.test_never_hardcoded_b1_over_b2` constructs a weak `SUSPECTED`/`WATCH`
B1 against a `CONFIRMED`/`CRITICAL` B2 and asserts B2 wins primary. `most_actionable_blocker_id`
is a genuinely separate field from `primary_blocker_id`, reported only when it differs
(`RankingMostActionableTests`). For identical input, repeated ranking produces an identical result
— `RankingDeterminismTests`, and every demo scenario re-run twice
(`DemoScenarioDeterminismTests`).

**One implementation nuance not spelled out in the design doc, documented here:** individual
blocker IDs are server-generated UUIDs, freshly assigned on every detection run — so the
tie-break at step (5) is *not* stable across two *separate* engine invocations if two blockers of
the *same type* also tie on criteria 1–4 (an edge case no demo scenario or realistic single-type
case produces; every ranking test that asserts cross-run determinism does so using fixed,
hand-assigned test IDs precisely to isolate this). Steps (1)–(4), which are what any real ranking
decision actually turns on, are fully deterministic across runs.

## L. Owner/action implementation

`actions.recommend_action(blocker) -> Optional[ActionRecommendation]`. Returns `None` only for
`RESOLVED`; every other raised status gets a recommendation — a lighter "verify the evidence"
recommendation for `SUSPECTED`/`INSUFFICIENT_EVIDENCE`/`CONFLICTED`, a substantive remediation
recommendation for `CONFIRMED`/`DETECTED`. `action_type` is drawn from a small fixed vocabulary
that is a **superset** of the existing, production `CaseAction.actionType` union (`'Legal
Verification'`, `'Fast-Track Compensation'`, `'Lok Adalat Settlement'`, `'Joint Mutation Camp'`,
`'Field Geo-Survey'`, `'Collector Hearing'`) plus exactly one new value B1 needed and none of the
six covered (`'Expedite Statutory Milestone'`). `rationale` always quotes the blocker's own
evidence descriptions — no LLM call anywhere in this package, no case-specific generated prose.
`precedent_refs` is always empty (precedent retrieval explicitly out of scope). Owner/authority
are copied straight from the blocker (already resolved per-class in `detection.py`, including
B4's non-single-valued cases).

## S. Remaining data limitations

Unchanged from the Step 7A audit's Data Gap table (`docs/step7a-blocker-engine-audit.md` §U), now
confirmed as actual, enforced ceilings in running code rather than a design intention:

- B2/B3 **cannot reach `CONFIRMED`** from any input this implementation accepts — a
  provenance-carrying title/record/compensation-dispute evidence entity (Data Gap rows B2-1,
  B3-1) does not exist. `secondary_ownership_observation` gives B2 a path to `CONFLICTED`, not to
  `CONFIRMED`.
- B3 has no representation at all for R&R obligations/completion or contested-amount
  (offered-vs-claimed) evidence (rows B3-2/B3-3) — `ParcelEvidenceInput` carries no such fields,
  so no code path can fabricate an evaluation of them.
- B4's one path to `CONFIRMED` requires a real, `VERIFIED`, in-scope `legal.stays.CourtStayEvent`
  — none of the five real seeded parcels exercised during verification had one on record, so none
  reached `CONFIRMED` in practice; this is the data gap manifesting exactly as predicted, not an
  engine defect.
- `interim_injunction`/`court_case_status` read from `Parcel.courtRecord` still cannot say *what*
  a restraint covers (possession vs. compensation vs. title) — case-subject classification (Data
  Gap row B3-4/B4-2) remains unbuilt; B3/B4 evidence descriptions say this explicitly rather than
  assuming a subject-matter.
- No S.30/S.38 `RuleSet` exists — B3/B4's `affects_possession=True`/`affected_clock_ids` hooks
  point at nothing today; they are interface stubs for a future legal-engine addition, not
  currently load-bearing.

## T. Recommended next step

Per the hard-stop instruction, this step does **not** proceed to the Exposure/Priority Engine, ML
upgrade, SHAP integration, precedent retrieval, what-if simulation, possession-impact engine,
route optimization, or frontend integration. The recommended next step, once this report is
reviewed, is **STEP 8 — EXPOSURE / PRIORITY ENGINE AUDIT & DESIGN**, consuming exactly the fields
this engine already exposes for that purpose (`severity`, confidence/status,
